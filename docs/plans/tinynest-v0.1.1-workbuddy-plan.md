# TinyNest V0.1.1 · WorkBuddy 下一阶段实施与量化验收计划

> 执行模型：WorkBuddy Hy4；专家技能：「高级开发工程师」吴八哥
> 项目：https://github.com/Sunywr/tinynest
> 起点：用户已完成 V0.1 的 PR 验证、合并，`main` 工作区干净（以实际 `git status` 与最新 SHA 再次核实）。
> 目标版本：**V0.1.1 核心家庭财务闭环**，不是 V0.2，不直接发布生产。

## 1. 本轮目标

在已有复式记账、账户、流水、信用工具、分期和投资基础实现之上，优先补全真正可用的业务闭环：

**家庭消费/收入 → 信用工具消费 → 出账 → 退款/分期 → 房贷/保险/固定付款 → 现金或信用工具还款 → 每日待办 → 首页核对。**

禁止用前端 Mock 冒充完成；完成的定义必须同时包含真实持久化、API、前端交互、自动化测试和可追溯的账务影响。

本轮**不做**邮箱自动抓账单、实时行情、AI 财务分析、银行/证券接口、原生 iOS App、复杂预算和正式生产部署。原先审查尚缺的投资费率写入接口、专业投资报表建议放 V0.1.2，除非修复本轮业务会直接依赖其能力。

## 3. 本轮实施范围与顺序

### M1 — 信用账单生命周期（优先 P0）

后端和前端补齐：

- 信用卡/花呗/美团月付/抖音月付/自定义信用工具创建、编辑、停用。
- 自定义账单开始/结束日、还款日、当月/次月偏移；月末 28/29/30/31、闰年和跨年处理。
- 账单状态：未出账、待还、部分还款、已还清、逾期。优先**由日期+账务事实推导**，避免数据库缓存状态与实际金额矛盾。
- 应还金额、已还、未还、可用额度、已用额度、额度使用率（额度未知显示“未配置”，不得计算假百分比）。
- 部分还款、提前还款、全额还款、退款回信用工具；现金还款不能计入新消费。
- 外部账单核对值与系统账单值分开存储，展示差额，不能静默覆盖历史交易。
- 账单周期修改不得静默重算已确认历史账单。

**门禁**：下文 T1 场景及账单日期边界全部通过；任何已入账动作有对应平衡分录。

### M2 — 房贷、贷款、保险和固定付款义务（优先 P0）

补齐真实 API、数据库关系、Vue 页面和自动化测试：

- 合同新增/编辑/停用、详情、期次计划、付款确认、部分付款、提前结清及冲正。
- 固定负债类型：房贷、其他贷款、保险、其他周期性付款义务。
- 贷款本金、利息、手续费与保险保费必须正确区分：贷款本金还款仅减负债，利息/费用计支出；保险费为费用，不能无缘无故增加贷款本金负债。
- 每期期次允许选择现金账户或信用工具实际付款；**信用卡付房贷/保险时，增加信用负债而非直接减少现金**。
- 未付款事项仍处于待处理，逾期与部分支付能正确计算剩余应付。

**门禁**：下文 T2 完整通过；每笔付款及冲正能够追溯到期次和账务分录。

### M3 — 分期完整性与退款联动（优先 P0）

- 检查现有分期创建、自动排期、期次付款、信用卡账单转分期是否形成完整闭环，只补确实缺失的路径。
- 合同本金合计、各期本金合计、费用合计、剩余应付始终守恒。
- **部分付款的本金/费用分配需要明确**。如果 10 项待确认口径尚未获得用户批准，V0.1.1 先使用每次付款时**显式录入/确认本金和费用拆分**的安全模式；不擅自按“先费用”“先本金”或比例分配。
- 分期部分退款、全额退款需要保留已支付历史，未来期次调整需显式确认，严禁静默删除分录。
- 信用卡原消费转分期后不得同时保留两份本金负债。

**门禁**：下文 T3 场景完整通过；同一付款请求重复提交不得双计入账。

### M4 — 自动到期任务与失败恢复（优先 P1）

- 实现轻量单实例定时调度；后端启动时可补扫，按 Asia/Shanghai 每日运行；不用 Redis/Kafka。
- 根据合同、账单和期次生成到期待办；允许实际付款后变更状态。自动任务**不得**自动标记已付款或扣款。
- 按 `household_id + contract/source + installment_no/due_date` 设计幂等业务键；跨家庭互不冲突。
- 幂等重复执行、重启补偿、失败日志与调度结果可追溯；日期可在测试中注入。
- 到期查询与本地提醒可实现，**本轮不发送真实短信或推送**。

**门禁**：同一任务重复执行 20 次仍只有一条逻辑待办；跨家庭隔离；未确认待办不改变资产和负债余额。

### M5 — 首页和统计可追溯（优先 P1）

- 保留现有收入、支出、现金流、资产负债、投资收益；新增应还、已还、逾期、未来 7/30 天待办、信用额度与分类/项目汇总。
- 支持自然月和自定义跨月/跨年起止日期。
- **收支按业务发生日；现金流按现金账户实际收付日；到期负债按约定到期日。**
- 同一消费不能同时被信用账单、分期和房贷统计为三次支出。
- 每个指标点击可进入明细；所有汇总须能从 SQLite 业务事实/复式分录重算；无数据时显示空状态而非 Mock。

**门禁**：下文 T4 场景通过，首页值与对应明细逐项相等。

### M6 — PC/iPhone 浏览器 E2E、CI、数据库演练（优先 P1）

- 用当前技术栈的浏览器测试工具执行至少 **12 条真实操作 E2E**，重点覆盖登录、账户、收入/支出、信用账单、部分还款、退款、固定负债、分期付款、待办、首页明细。前端真实访问 API，不用假保存成功。
- PC 1440px / 平板 768px / 手机 390px 三套视口：无阻断、文字数字不溢出、关键输入可操作；保持 A「奶油团子」视觉和原始图标。
- 验证无未授权敏感 API、跨家庭读取/写入、CSRF/会话缺陷；在本地验证 CI 配置和所有同等命令；如尚未获得 push 授权，GitHub Actions 真实状态标 `CI_UNVERIFIED`，不得擅自推送来触发。
- 在隔离 SQLite 测试库中完成从空库迁移、重启、备份、恢复、`quick_check`/`foreign_key_check`；禁止触碰真实账本。
- 若缺浏览器或 iPhone 设备，明确标记 `UNVERIFIED`，绝不虚报“已实机通过”。

**门禁**：P0 = 0、P1 = 0，所有必要核心测试实际通过。此处“可演示/可合并”不等于允许生产录入真实财务数据。

## 4. 核心账务不变量（不得违反）

1. **每笔分录借贷相等；业务单据和分录必须在同一 SQLite 事务中完成。**
2. 人民币金额采用整数分，证券份额/价格用定点数，不用浮点数参与入账。
3. 已入账交易不可物理删除，纠错必须冲正并保留关联、审计信息。
4. 信用消费增加支出和信用负债，但不影响现金；信用还款只减少现金和信用负债。
5. 自有账户转账不产生收入或支出。
6. 贷款本金偿还只减少负债，利息/费用部分单独计支出；信用支付产生新的信用负债。
7. 分期消费本金仅确认一次；每期偿还只清结分期负债、确认应有费用。
8. 自动待办不得自动生成已付款流水。
9. 退款冲减原交易分类/项目，累计退款不得超过可退金额。
10. 已确认数据可从明细和分录重建；跨家庭访问必须 SQL 层隔离。
11. UTC 存储审计时刻，Asia/Shanghai 用于家庭业务日期和到期日。
12. 新增核心写 API 必须支持业务幂等，重复提交或重试不得重复入账。

## 5. 必须自动化的数值验收样例

**T1 信用卡全流程**：现金初始 10,000 元，卡额度 20,000 元。信用卡消费 1,000 元 → 费用 +1,000、信用负债 +1,000、现金不变、可用额度 19,000。现金还款 600 元 → 现金 -600、信用负债 -600、费用不变、未还 400、可用额度 19,600。原消费退款 300 元退回卡 → 费用净额 -300、信用负债 -300、未还 100、可用额度 19,900。再还 100 元后负债归零。还需测月末、闰年、跨年、提前还款、逾期。

**T2 信用卡付房贷**：房贷期次 2,000 元（本金 1,500 元、利息 500 元），用信用卡支付 → 房贷本金负债 -1,500、利息费用 +500、信用负债 +2,000、现金不变；再用现金还信用卡 2,000 → 现金 -2,000、信用负债 -2,000，房贷和利息**不得重复计入**。

**T3 分期守恒**：合同本金 3,000 元、手续费 90 元、3 期 → 总应付 3,090 元；一期本金 1,000、费用 30、应付 1,030。若先付 515 元，必须明确该笔实际付款的本金/费用拆分且合计 515；一期剩余应付 515，状态“部分付款”；不得自行假定分配顺序。调度执行 20 次不重复生成待办。

**T4 三套统计口径**：跨月信用卡消费、次月退款、之后月份的信用还款，以及同月贷款本金与利息拆分。断言每期收支、现金流、到期应付的日期与金额分别正确，所有卡片均可追溯到明细。

**T5 家庭隔离**：隔离测试库里 A/B 两家庭均有账户、信用账单、贷款、分期、还款。A 的令牌读写 B 的任一业务必须拒绝；A/B 各自统计、调度、幂等键严格隔离。

## 7. 10 项账务口径与发布边界

- 完整读取 `docs/reviews/v0.1-accounting-decisions.md`，逐项记录当前代码行为、推荐规则及影响范围。
- **已确认数由用户真实确认记录决定**，不能因“代码有默认实现”或“测试通过”而代替用户确认。

- `PRODUCTION_READY` 仍要求：用户确认 10 项账务口径、必要模块完整、双服务器 HTTPS 与可信代理实测、iPhone Safari PWA 实机、完整 E2E 与备份恢复、安全检查、真实 CI 通过。不得直接部署正式域名或录入真实财务数据。
