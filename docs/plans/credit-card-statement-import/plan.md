# 信用卡账单导入与对账计划

用户可为自己的 QQ 或 163 邮箱配置授权码并绑定指定信用卡。系统读取银行账单，有完整明细时对账并自动导入缺失流水，仅有应还金额时显示待还并引导对账。用户可上传银行 XLS 补录明细。占位流水仅适用于后续能够独立确认本期未入账消费、且已确认占位账务口径的场景。

> **占位口径已于 2026-11-26 由用户确认为「写待补明细占位流水」**（金额=银行本期应还、日期=还款截止日、明细补齐后冲正归零），本句「需已确认」的条件即由此满足；实现与验证见[实施进度](实施进度.md)「口径推翻」与「本轮交付」两节。本计划正文保留原文，不再把占位当作待决项。

## 接手流程

1. 收到「继续实施未完成的计划」后，从仓库根目录读 `AGENTS.md`、本计划和[实施进度](实施进度.md)。核对工作树、当前 SHA 和远端基线，保留已有改动。按仓库规范同步 CodeGraph 索引后，用 CodeGraph 检查信用卡还款计划、流水写入及冲正、邮件配置、权限、迁移与 Web 入口。以 V2 契约和当前代码为准。
2. 核实已完成项的实现和证据，继续首个可执行的未完成项。需要用户补充时，每轮最多三个问题，每题说明「需要的材料或决定、原因、可选方案、推荐默认值」。等待期间可做独立的测试准备与接口设计。
3. 将用户确认、脱敏证据位置、候选 SHA、实际验证和下一步写入实施进度。仅把有证据的项目记为完成。

## 实施顺序

### P0 · 核对基线与账务口径

- 按 V2 新增账单导入能力。银行报告的本期应还用于账单对账和待还展示，账本余额仍从分录计算，信用卡还款沿用转账。同一账单的银行待还与现有还款计划不得重复计债。
- 确认占位金额、业务日期、支出分类与报表影响。应还可能包含结转、费用、退款或已还款。仅能识别总应还时先记录待还与待对账，待用户确认占位金额和口径后才写账本。
- 落定增量迁移、HTTP 契约和权限后记录在进度页。SQLite 与 MySQL 都走 V2 迁移，MySQL 迁移须可重复执行。所有财务查询在 SQL 层限定家庭，账务使用整数分和上海业务日期。

### P1 · 邮箱与解析

- 在「我的」增加个人邮箱配置、测试、更换授权码和停用。只可绑定有操作权限的信用卡。服务端通过 IMAP over TLS 读信，SMTP 用于发信。以服务商官方资料和授权测试邮箱确认接入参数。
- 授权码加密存储，接口和日志不回显。停用后停止拉取。按配置查找匹配银行与信用卡的候选邮件，解析账期、应还、到期日和明细。格式未知、卡片歧义或字段冲突时标记待处理。

### P2 · 对账与入账

- 校验通过的完整明细匹配已有有效流水，只自动导入明确缺失的明细。匹配歧义交由用户确认。
- 仅有汇总时展示待还，并在流水中提示对账。已有当期流水时先匹配，差额待核对。完全没有当期流水且占位金额已确认时，生成一条「待补明细」流水。关闭补录提醒后仍可上传明细。
- 使用家庭、信用卡账户、账期和来源标识保证幂等，覆盖重复拉取、重复上传、不同来源重叠和并发。业务记录、分录、对账关联和审计写入同一数据库事务。

### P3 · XLS 补录

- 用浦发、中信的脱敏原格式样本确定首批支持的 XLS 版式。只读取单元格数据，限制文件大小和行数。预览展示账期、匹配项、新增项和未解释差额，用户确认后入账。
- 有可核对的占位时，在同一事务内按占位原业务日冲正、关联已有流水、补录缺失明细并写审计。无占位时导入缺失明细。部分补录、金额不符、疑似重复或跨账期时保留待对账状态，禁止自动冲掉整笔占位。
- **落地口径（2026-11-26 实施后回填）**：首批只做**浦发**，四类分开、**只入账判定为「消费」的行**，`occurred_on` 取银行的**交易日期**（三项均由用户确认，见[实施进度](实施进度.md)）。服务端**不自动冲正占位**——同账期还有未冲正的待补明细占位时整批以 409 `placeholder_not_reversed` 拒绝并提示先冲正，理由是「冲掉一笔用户确认过的占位」与「补录一批明细」是两件事，合并成一次自动写账会让用户无法预判账本变化；上一条的「在同一事务内按占位原业务日冲正」因此按**拒绝 + 人工先行冲正**实现，同一事务保证的是本批补录自身全有或全无。幂等粒度为**行**（`statement_details` 的 `row_key`+`seq`），预览与入账是两条独立路由（第 74、75 条），预览阶段零写入。

### P4 · 验证与发布

- 通过邮箱配置、邮件处理、待还、流水和 XLS 上传的正常入口跑回归。记录候选 SHA、环境、命令与结果。
- 分别记录本地验证、服务商与银行样本实测、预发布、生产部署和生产验收。生产操作由用户授权。

## 与使用者交互

1. **样本与银行。** 请选优先支持的银行，可先验证浦发或中信，也可先覆盖两家。请提供已有的脱敏汇总邮件、明细邮件和相应原格式 XLS 副本，用于确认字段和版式。建议从样本最齐全的一家开始。保留邮件结构、账期、字段名、金额正负及表格布局，身份与卡号用一致的虚构值替换。授权码、完整卡号及未脱敏账单不要交给 Agent 或存入仓库。
2. **账务规则。** 取样本中一笔账单，向使用者列出本期消费、总应还、已有流水和待核差额。请确认仅有应还时是保留待对账，还是在可确定本期未入账消费后生成占位，并确认日期、分类及报表影响。结合样本核对结转、还款和退款。默认在金额含义未确认时保持只读对账。
3. **接入与验收。** 请选第一个邮箱和银行组合、首拉历史范围及拉取频率，例如先用一套授权测试邮箱验证一个账期，再扩大范围。约定由使用者在应用内输入授权码。缺少样本或实机证据的组合逐项标记 `UNVERIFIED`。

## 验收用例

| 场景 | 预期 |
| --- | --- |
| 同卡同账期重复拉取、补传或并发 | 同一账单只形成一笔待还，明细只入账一次 |
| 已有部分流水的完整账单 | 匹配已有流水，只导入缺失明细 |
| 仅应还且无当期流水 | 显示待还。金额确认后至多一条占位，未确认时账本无新增分录 |
| 保留占位，之后补传完整 XLS | 可关闭提醒并再次补录。替换后账务只计算一次 |
| 部分补录、金额不符、疑似重复、跨账期 | 待对账，不自动冲掉整笔占位 |
| 冲正后写入失败 | 整笔事务回滚，原占位和对账状态有效 |
| 跨家庭访问、邮箱停用 | 阻止越权读写，停用后停止拉取 |
| SQLite 和 MySQL 既有 V2 库 | 增量迁移后历史分录、余额与统计通过回归 |
