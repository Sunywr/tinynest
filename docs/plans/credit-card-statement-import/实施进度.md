## 本轮交付（2026-11-26 第四轮）：账单明细补录（P3）

### 口径（用户确认，非默认值）

2026-11-26 的三项选择构成实现口径，逐项来自用户答复而非按默认值补齐：

- **首批银行 = 浦发**：列序按浦发导出的 XLS 实测版式硬编码为常量（`交易日期 / 入账日期 / 交易摘要 / 卡号末四位 / 卡种 / 币种 / 金额`，`detailCol*`），其他版式解析失败时按「未识别」登记而不是猜列位。中信版式（列为「入账日期」）尚未落地，属后续增量。
- **四类分开，只入账消费**：`kind ∈ charge / refund / payment / fee / review`，只有 `charge` 写分录。判定词表固定三组（退款：退款/退货/冲退；还款或转入：还款/转入/转账/汇入/充值/存入/赎回/溢缴款；费用利息：年费/手续费/利息/违约金/滞纳金/超限费/取现费/分期费/工本费/服务费/罚息），且**负数金额本身不是退款的证据**——摘要未标明退款的负数行落 `review`。非 CNY、卡尾不符、金额或日期无法解析同样落 `review`。
- **业务日期 = 银行的交易日期**，不是记账/入账日期；入账日期只登记在 `statement_details.post_on` 供人工核对。

### 数据模型与迁移（014）

- `statement_details`：一行 = 电子表格一行，存原样单元格派生值（`row_key`、`row_no`、`seq`、`card_tail`、`kind`、`state`、`txn_on`、`post_on`、`description`、`amount_minor`、`currency`、`review_reason`、`source_digest`、`transaction_id`）。
- **幂等粒度是行**：`UNIQUE(household_id, account_id, row_key, seq)`；`row_key = SHA-256(交易日期或原文, 金额或原文, 卡尾, 币种, 摘要)`，`seq` 让同一天两笔完全相同的消费各自成行而不被静默合并。`UNIQUE(household_id, transaction_id)` 挡住同一行二次入账。
- `state ∈ imported / matched / held` 落库；`missing`（账本尚无对应流水、待入账）只在响应里出现，**不落库**——否则重传时无法区分「已经决定不入账」和「上次没入账」。
- 外键：`households` / `accounts` / `transactions`，以及复合 `FOREIGN KEY(household_id, statement_id) REFERENCES card_statements(household_id,id) ON DELETE CASCADE`。SQLite 与 MySQL 同名同义；MySQL 版全部内联在 `CREATE TABLE IF NOT EXISTS` 里以保证可重跑。
- 清理归类：`statement_details` 落在「银行账单与绑卡」组，且在 `DeleteOrder()` 里排在 `card_statement_sources`、`card_statements`、`transactions`、`accounts` **之前**（它同时引用账单与流水）。清单随之从 55/23 变为 **56 个表名 / 24 张存在 / 32 个 V1 遗留名**；`TestPurgeClearsCardStatementTables` 与 `TestStatementTablesSortBeforeTheirParentsInDeleteOrder` 覆盖，`TestV2SchemaHasNoUnclassifiedTables` 保证漏归类会被 `verify` 挡下。

### API（第 74–75 条路由）

| 方法 | 路径 | 写账本 | 要点 |
| --- | --- | --- | --- |
| `POST` | `/api/v1/accounts/{id}/statement-detail-preview` | **否** | 与导入同一套解析/判定，逐行回显 `kind`/`state`/`reason`/`already_imported` 与待入账笔数、金额；全树零 SQL 写 |
| `POST` | `/api/v1/accounts/{id}/statement-detail-import` | 是（仅 `charge` 且账本无对应流水的行） | 一笔「账单补录」信用卡支出（借 `5010:cat_<hh>_statement_detail` / 贷 `2010:<卡>`），`occurred_on`=交易日期；明细行、流水、分录、审计、`card_statement_sources(kind='xls')` 同一事务 |

- 请求体只接受 `rows`、`card_tail`、可选 `statement_id`；**金额、日期、分类一律由服务端从银行原文与账本推出，客户端不可提交**。
- 错误：400 `invalid_request`（空行 / 缺卡尾）、400 `too_many_rows`（>3000 行，请求体本身另有 `decode()` 上限）、404（非信用卡 / 已停用 / 他家庭 / 未知 `statement_id`）、409 `placeholder_not_reversed`（同账期还有未冲正占位，响应带那笔占位的 `transaction_id`/金额/账期，**服务端不自动冲正**）。
- 匹配：同日同卡同金额的账本流水唯一命中 → `matched` 不重复入账；**两笔候选 → `held`「无法唯一对应」，不猜**。

### 本轮发现的缺陷（先补测试再修）

1. **`category_id` 是死字段且能变成 500**：`StatementDetailImport.vue` 只提交 `rows`/`card_tail`/`statement_id`（`apps/web/src/components/StatementDetailImport.vue:72-75`），但 Go 侧请求结构仍收 `category_id`，并有一条分支在分类是收入 / 已软删 / 不存在时返回 `sql.ErrNoRows` 或 `补录分类必须是支出`——后者经 `internalErr` 变成 500，等于让客户端一个字段把补录打成服务器错误。修法是把该字段从契约里删掉（分类固定由服务端 ensure，与 013 的 `placeholderCategory()` 同形），并补 `TestStatementDetailImportIgnoresClientCategory` 断言三种非法 `category_id` 提交仍然 200 且入账分类是「账单补录」。
2. **响应多报了金额**：`booked_minor` / 成功提示原本累计所有 `charge` 行的金额，包括上一次已入账、这次只是重传的行。改为只报**本次真正写入**的 `postedMinor`，`TestStatementDetailImportIsIdempotentPerLine` 用「只补新增那一行」断言 `amount_minor` 恰为该行的 7,770 分。
3. **MySQL 014 与 SQLite 方言分歧**：`description` 在 MySQL 侧写成 `VARCHAR(191)`，银行摘要常有超长行，`STRICT_TRANS_TABLES` 下会 1406 回滚**整批**（SQLite 的 `TEXT` 不报错，本机全绿而生产炸）；同时 MySQL 缺 `transaction_id → transactions` 外键。两处都对齐 SQLite（`description TEXT`、补外键），再在隔离 8.4.7 实例重跑全链证明。**SQLite 侧文件未改**，因此不触发本地开发库的校验和漂移，生产也只跑到 013、无需回填。

## 口径推翻（2026-11-26 第三轮）

第二轮记下的「账本零新增分录 / 不实现占位流水」是**对用户选项描述的推断**，且当时已标注「选项标签与描述矛盾，需回读确认」。用户随后直接用自由文本回答，矛盾随之结案——原话：

> 「关于第2个回答，我思考的是本来流水是用明细录入，但由于用户懒得上传明细，那就先创建个待补明细的流水，金额是信用卡当期账单的还款金额，创建时间是信用卡的还款截止时间。」

以及更早一句：

> 「明细虽然重要，但是关注实时的现金流也同样重要，所以还款金额需要占位参与现金流的推算」

据此确定的口径（本轮按此实现，**不是**按默认值自行补充）：

- 占位是一笔**真实的信用卡支出分录**：借 `5010:cat_<householdID>_pending`（分类「待补明细」）／贷 `2010:<信用卡>`，金额取**银行已报出的本期应还**，`occurred_on` = **还款截止日**。不动现金账户，因此现金余额不因它变化，但还款计划的现金缺口会提前把这笔占住。
- 由**用户点按钮**显式触发（资产页还款计划卡片上的「生成待补流水」），服务端先弹确认（卡名／账期／金额／截止日），不是 V1 的 IMAP 自动过账，也不引入分期、利息、最低还款。
- 明细补录之后**冲正即归零**：走既有 `DELETE /api/v1/transactions/{id}`（V2 没有独立的 `POST …/reversal` 路由，删除即写 `reversal_of` 冲正），冲正沿用原 `occurred_on`，所以截止日所在月的净额归零、不留余额；删除后 `placeholder_state` 变 `reversed`，按钮消失。
- 占位**不改变** `ledger_charge_minor` / `difference_minor`：账单页差额的 SQL 只统计 `occurred_on` 落在 `[period_start_on, period_end_on]` 内的已入账支出，而占位的 `occurred_on = due_on`（账期结束之后），**天然落在窗口之外**——不是靠显式的排除条件，也不是特判，因此不会出现「占位自己把自己的差额抹平」。
- 仍不恢复 V1 模块：`internal/credit` 不存在，`card_statements` 依旧只存银行报的汇总，`statement_placeholders` 只存「账单 ↔ 占位流水」的一对一关联加银行自己的账期日期。


## 本轮交付（2026-11-26 第三轮）：待补明细占位

按上述口径实现。如实说明测试时序：本轮在同一批改动里交付实现与用例，`credit_statement_placeholder_test.go` 的 10 个顶层用例与 3 个门禁子测试**在当前代码上全部通过**（SQLite 全量 + 隔离 MySQL 逐库单跑），但**没有留存「实现前先跑红」的日志**，故不声称已按红→绿留证。对守卫的敏感性只由 `RefusedWhenCycleAlreadyRecorded` 与 `GuardsStatementState` 的断言形态体现（它们直接断言 409 码与三张表零脏行，去掉任一门禁即会失败），这一点尚未像 `TestStatementSyncRechecksMailboxBeforeWrite` 那样做过变异复核。

### 数据模型与迁移

- 新迁移 `013_statement_placeholders.sql`，SQLite 与 MySQL **两份同名文件**（每方言现 **13 个**迁移）。表 `statement_placeholders` 存 `household_id / statement_id / transaction_id` 与**银行自己的** `period_start_on / period_end_on / due_on`（后三个可空，值来自 `card_statements` 而非卡的当前配置，这样还款日后来被改也仍按当期窗口归档）。
- 约束即幂等：主键 `(household_id, statement_id)` 让同一账单只有一条占位；`UNIQUE (household_id, transaction_id)` 让一条流水只挂一张账单；`KEY (household_id, due_on)` 供推算视图按截止日取数；外键 `→households(id)`、`→transactions(id)`（两条都**不带 CASCADE**，防止删家庭/流水时静默吞掉占位关系），以及复合外键 `(household_id, statement_id) → card_statements(household_id, id) ON DELETE CASCADE`——删账单汇总时占位关联随账单消失，但**已写入的分录与流水不受影响**（分录不可变）。
- MySQL 8.4.7 `SHOW CREATE TABLE statement_placeholders` 实测：列 `household_id/statement_id/transaction_id` NOT NULL、`period_start_on` 可空、`period_end_on`/`due_on`/`created_at`，字符集 `utf8mb4_0900_ai_ci`（索引列 `varchar(191)`）；`PRIMARY KEY (household_id,statement_id)`、`UNIQUE KEY uq_statement_placeholders_transaction`、`KEY idx_statement_placeholders_due`、`ibfk_1/2/3`（`ibfk_3` 带 `ON DELETE CASCADE`），引擎 InnoDB。
- 013 的 SHA-256（迁移账本用，改动文件即触发 baseline 守卫拒绝启动）：MySQL `5cfe1b24bb5730c1249c81e4218c369885aacbbeda0602d4d374214a72df40e4`、SQLite `5a2fa00be67dab71f40c23157ba7b3254d80b771fc42eb10126567a04ae3e786`。
- MySQL 文件可重复执行：`CREATE TABLE IF NOT EXISTS` + 内联索引，无裸 `ALTER`，符合 V2「DDL 隐式提交」的幂等要求。空库 `SOURCE` 001–013 **连跑两遍** → `errors=0 tables=38`（两遍相同），证明重放不失败、纯 SQL 链也是 38 张。
- 表数当前口径（本轮在两方言逐张清点）：纯 SQL 链 **38 张**；MySQL 运行时 **39**（加 `schema_migrations`）；SQLite 具名 **39** / 含 `sqlite_sequence` **40**。清理清单随之从 54/22 变为 **55 个表名 / 23 张存在 / 32 个 V1 遗留名**，`PurgeTableSet()` = `DeleteOrder()` = 55；`statement_placeholders` 归入「银行账单与绑卡」组，并在 `deleteOrder` 里排在该组**最前**（`card_statement_sources`、`card_statements` 之前）——因为它同时引用账单与流水，必须先删关联，它引用的分录/流水行留到各自的轮次再删；全程不关闭外键，跑通即证明没留下孤儿行。

### API

- **`POST /api/v1/accounts/{id}/credit-statement-placeholder`**（`internal/api/credit_statement_placeholder.go`，新文件）。请求体只有 `{"statement_id":"…"}`：`statement_id` 必填非空（缺失 400 `invalid_request`），**金额与日期都不接受客户端输入**——服务端按 `(household_id, account_id, id)` 从已落库的 `card_statements` 读回 `amount_due_minor`、`period_start_on`、`period_end_on` 与 `due_on`（SQL 只有这一条 SELECT，天然按家庭隔离）；截止日缺失时回落到卡片配置的 `due_day`，配合账单日推出当期截止日（`DerivesDeadlineFromCardConfig`：银行只报了期末、没报截止日，占位仍落到 `2026-11-25`）；该路径**不访问邮箱**，也忽略 `provider` 查询参数。
- 门禁：账户必须是**本家庭的、未停用的信用卡**（`loadActiveAccount` + `Kind=="credit"`，否则 404）；账单必须已落库且属于这张卡；去重靠 `statement_placeholders` 的主键 `(household_id, statement_id)`，另写服务器派生的幂等键 `statement-placeholder:<statement_id>`（**不读客户端 `Idempotency-Key`**）。**重复点击返回 409 `placeholder_exists`，响应体带既有那条的 `transaction_id`**（`ReplayReturnsExistingTransaction` 同时断言三张表计数不变，即重放绝不写第二笔占位支出）——这与 `docs/api-v2.md` §11 的契约一致，不是「二次调用返回 201」。
- 409 拒绝码（与 `docs/api-v2.md` §11 逐项一致）：`cycle_not_closed`（账期未结束）、`amount_unknown`（银行没报出应还金额）、`due_date_unknown`（银行截止日无法解析、或回落卡片配置后仍算不出）、`cycle_already_recorded`（同账期账本已有消费分录）、`placeholder_exists`、`placeholder_reversed`；账户不存在/已停用/非信用卡、`statement_id` 不属于本家庭这张卡走 **404**，`viewer` 走 **403**，缺 `statement_id` 走 **400**。三个 `GuardsStatementState` 子测试覆盖前三个码，各自断言「409 + `journal_entries`/`transactions`/`statement_placeholders` 三张表计数仍为 0」，即**拒绝不留任何脏行**。
- 事务：流水、配平分录（2 行）、占位关联行、审计日志在同一次 `WithTx` 内写入，事务内还重验「账期是否已被入账」与「占位是否已存在」两件事（并发补录明细与重复点击都不能挤进检查与写入之间）。`RowsAreHouseholdConsistent` 断言把**别的家庭**绑到本家庭账单上的关联行被复合外键直接拒绝，并核对关联行与流水行的 `household_id` 相同。
- `GET /api/v1/credit-statements` 每条账单新增 `placeholder_transaction_id`（无占位为 `null`，走 `nullable()`）与 `placeholder_state`（`''` 无占位 / `awaiting_detail` 占位仍有效 / `reversed` 已被冲正），账单页由此能显示「已占位／已冲正」而不是只有比对差额；成功创建返回 **201** 与 `{transaction_id, statement_id, account_id, amount_minor, occurred_on == due_on, period_start_on(可为 null), category_name:"待补明细"}`。
- 路由总数 **73**：`Register wired 73 routes (budget 73)`，`maxRoutes = 73`（`internal/api/helpers.go:32`）。
- 权限与隔离（`TestStatementPlaceholderPermissionsAndScoping`）：他家庭的账单与不存在的账单都返回 **404**（不给存在性信号）；CSRF 令牌错误返回 **403**；把用户降为 `viewer` 后返回 **403**；以上被拒的四种请求逐一断言 `transactions`/`journal_entries`/`statement_placeholders` 计数为 0，即**鉴权失败绝不留下分录**。读取账单的 SQL 全部带 `household_id`。

### 账务不变量与统计口径

- 分录形态：借 `5010:cat_<householdID>_pending` / 贷 `2010:<信用卡账户的 ledger_code>`，金额 = 银行本期应还（整数分），`occurred_on = due_on`。**不动现金账户**，所以现金余额不变，只把未来要付的钱在推算里占住。
- 「待补明细」分类 `cat_<householdID>_pending` 由 handler 在同一事务内**按需创建**（emoji `receipt`、颜色 `6`），不是 `db.DefaultCategories` / `SeedForHousehold` 的种子——这样不改动种子基线、也不给历史家庭补插分类行；`TestDefaultCategoriesCarryIconAndColor` 仍断言 21 个内置默认分类，占位分类不在种子里。
- 纠错走既有的**删除即冲正**路径 `DELETE /api/v1/transactions/{id}`（V2 没有独立的 `POST …/reversal` 路由，注册表见 `internal/api/setup.go`）：`ReversalNetsThePeriodToZero` 断言删除后按 `due_on` 所在月聚合的「待补明细」净额归零、`total_debt_minor`/`overdue_minor` 回 0，且账单行的 `placeholder_state` 变 `reversed`；流水与分录行都不物理删除。
- 落库形状（`TestStatementPlaceholderWritesAwaitingDetailTransaction` 逐值断言）：一次调用写 **1 条 `transactions` + 1 条 `journal_entries` + 2 条 `journal_lines` + 1 行 `statement_placeholders` + 1 条审计**，响应 201 并回显 `amount_minor`/`occurred_on`/`period_end_on`/`due_on`/`account_id`；流水 `type=expense`、`status=posted`、`category_name=待补明细`。
- 统计与推算的可见结果：11 月的分类统计里出现「待补明细」= 银行应还金额（**占位确实计入支出报表**，这是用户要的现金流效果）；还款计划 `total_debt_minor` = 该金额，且因按银行账期归档而计入 **`overdue_minor`（逾期）而不是 `unbilled_minor`**——账单已出账、截止日已过，就不该显示成「未出账」。
- 已入账分录不变式未被触碰：占位与冲正都只新增行，不 UPDATE / DELETE 分录；`GET /accounts?include=credit_debt` 的 `total_debt_minor` 由这条占位增加、被删除冲正后归零，`overdue_minor` 同步（用例 `ReversalNetsThePeriodToZero` 断言两者回 0）。
- 补明细（P2 的明细录入）与占位是两条独立路径：明细照常按消费日记 `5010:<分类>`、日期是消费日；占位记在 `due_on`。两者日期不同，账单页的 `ledger_charge_minor` / `difference_minor` 因窗口条件而**不会把占位算成当期消费**（机制见「口径推翻」末条：靠 `period_start_on..period_end_on` 区间，不是显式排除条件），也不会自己把自己的差额抹平。

### 还款计划的派生例外（`internal/api/credit_debt.go`）

还款计划原本要求「只读派生、不写分录、不缓存、不读 `card_statements`」。本轮**没有**让推算去读 `card_statements`，而是在派生 SQL 里给占位分录开了两处口子（都就地写了注释）：

1. `scanCreditCardRows` 的 WHERE 中，信用卡支出分支由 `… AND e.occurred_on<=?` 改为 `… AND (p.statement_id IS NOT NULL OR e.occurred_on<=?)`（新增 `LEFT JOIN statement_placeholders p ON p.household_id=t.household_id AND p.transaction_id=t.id`）：**占位行即使 `occurred_on` 在未来也计入待还**，普通支出仍只统计到今天，因此现金缺口 `cash_needed_minor` 会提前把这笔占住；
2. 账期窗口计算新增 `case placeholderEnd.Valid:`：当关联的占位在 `statement_placeholders` 里带着**银行自己的** `period_start_on/period_end_on/due_on` 时，用这三个值覆盖按卡片 `statement_day/due_day` 现算的 `cycleFor()` 结果，避免「用户后来改了还款日 → 历史账单的占位被算进错误周期、逾期判定跟着错」。

同步查询对没有占位的账单传空 `sql.NullString{}`，行为与 013 之前一致（9 条既有 sync/对账/绑卡回归在 SQLite 与隔离 MySQL 上全绿即为此证明）。

## P2 已实现（2026-11-25，提交 `50b6752`）

范围为「银行汇总落库 + 按账期只读比对」，不含明细匹配、占位与自动入账。

> 本节是 2026-11-25 的记录，数字保持原样；**当前口径已变**：两方言各 **13** 个迁移（新增 `013_statement_placeholders`）、路由 **73** 条、`GET /credit-statements` 每条账单多 `placeholder_transaction_id` 与 `placeholder_state` 两个字段，且**占位流水已在同日第三轮实现**——下面「不含…占位…」与「该路径不写 `transactions`、`journal_entries`、`journal_lines`」两句只描述 012 那条同步路径，同步本身仍不写分录；写分录的是**另一条** `POST …/credit-statement-placeholder`。见文首「本轮交付」。

- 迁移 `012_card_statements.sql`（SQLite 与 MySQL 各一份，两方言现各 12 个文件）新增 `card_statements` 与 `card_statement_sources`。表名故意避开 V1 已退役的 `credit_statements` / `credit_statement_items`，让 `tinynest-admin` 清理清单继续表示 V1 语义。MySQL 版只用 `CREATE TABLE IF NOT EXISTS` 与内联索引、约束，结构上可重跑。
- 契约：`POST /api/v1/accounts/{id}/credit-statement-sync?provider={qq|163}&version={n}` 返回 `{since,created,linked,conflicts,needs_review,items[]}`；`GET /api/v1/credit-statements` 返回 `{items:[{id,account_id,account_name,period_start_on,period_end_on,due_on,currency,amount_due_minor,status,review_reason,source_count,ledger_charge_minor,difference_minor}]}`，按期末、卡名、id 排序。路由预算由 70 提高到 72，实测 `Register wired 72 routes`。
- 幂等：账单唯一键 `household_id + account_id + period_end_on`；来源唯一键 `household_id + digest`，`digest` 为服务商、用户、IMAP UID、账户、期末、到期日、卡尾号、金额与币种的 SHA-256。同邮件重放不新增账单，同账期新邮件只增加来源。
- 与草案的偏离：来源键未使用 `UIDVALIDITY`。现行 IMAP 只读打开不解析 `EXAMINE` 响应，取该值需要改动协议层；改用内容摘要承担重放识别，UID 仅作为摘要输入保留。
- 只存「完整识别」的汇总（账期、非负人民币应还、无待核对标记）。金额冲突保留首次记录的银行金额，只补 `review_reason`；未识别邮件只计数，不落库。审计仅在有新账单或冲突时写一条 `sync_card_statement`。
- 账本比对：`period_start_on` 由卡片 `statement_day` 推导为上一账期期末的次日；未配置账单日时 `period_start_on`、`ledger_charge_minor`、`difference_minor` 一律为 `NULL`。`ledger_charge_minor` 在 SQL 层按家庭与账户码聚合同周期已入账消费（贷记卡科目取贷−借），与现行还款计划口径一致。
- 账务不变量：该路径不写 `transactions`、`journal_entries`、`journal_lines`，也不改账户余额；用例断言同步前后 `GET /accounts?include=credit_debt` 的 `total_debt_minor` 不变。
- 权限与隔离：写操作需成员以上与 CSRF，只读角色 403；未绑定或他卡 404；跨家庭账单与来源查询无结果，跨家庭来源行被 `(household_id, statement_id)` 复合外键拒绝。
- 并发：邮箱读取后与写入事务内各重验一次配置版本与绑定。停用或换码与拉取并发时返回 409 且零落库；`TestStatementSyncRechecksMailboxBeforeWrite` 在移除该重验后会退化为 200 并写入账单，已实测确认该用例对守卫敏感。

### XLS 样本结构（2026-11-26 按用户提供的受控本地样本实测）

用仓库已装的 SheetJS（`apps/web/node_modules/xlsx` 0.20.3）在本机临时脚本里读结构，**只导出列名、单元格类型、数字格式串与形状掩码，明细金额、商户名、卡尾号一律不落本页、不进 git、不进日志**。样本目录记为受控引用：`D:\Packages\Browser\`（1 个中信文件 + 1 个子目录内 5 个浦发月度文件，另有 1 份重复下载件；文件名含持卡人与报表编号，故不写全名）。

- 两份都是 OLE2 复合文档（文件头 `d0cf11e0a1b11ae1`，即 BIFF8 `.xls`），单工作表，**所有单元格 `t='s'`（文本）**：没有数值型或日期型单元格，因此解析是纯字符串规则，不受数字格式与序列号日期歧义影响，也不需要时区换算。
- **浦发**，工作表 `账单明细`：表头在**第 1 行**，**8 列** = 交易日期 / 记账日期 / 交易摘要 / 卡号末四位 / 卡片类型 / 交易币种 / 交易金额 / 原始交易金额&币种；日期为紧凑文本 `YYYYMMDD`；金额文本可带负号；末列形如 `金额(CNY)`；数据行按交易日期**升序**；`卡片类型` 本样本恒为「主卡」，卡号末四位单值。
- **中信**，工作表 `本期账单明细(人民币)`：**第 1 行是标题行**（仅 A1 有值、其余 7 格空），表头在**第 2 行**，**8 列** = 交易日期 / 入账日期 / 交易描述 / 卡末四位 / 交易币种 / 结算币种 / 交易金额 / 结算金额；日期为文本 `YYYY-MM-DD`；数据行按交易日期**降序**（最新在前）；本样本交易金额与结算金额同值。
- 因此两家共用同一套列位映射**不成立**：起始行不同（浦发 1、中信 2）、日期写法不同（`YYYYMMDD` 与 `YYYY-MM-DD`）、排序方向相反、金额列名不同（交易金额/结算金额 vs 交易金额/原始交易金额&币种）。解析器必须按银行分支，并先跳过标题行。
- **账期窗口实测**（5 个浦发月度文件，逐文件取首末交易日期）：文件名月份为 `M` 的账单覆盖 **`(M−1) 月 8 日` 至 `M 月 7 日`**，即账单日为每月 7 日；实测 `202610` = 09-08…10-07、`202611` = 10-26…11-07、`202608` = 07-27…08-07、`202609` = 08-23…08-29、`202607` = 06-10…06-29（稀疏月份只出现窗口内的部分日期，从未越过 7 日边界）。中信样本覆盖 10-21…11-14，与账单日 14 日一致。**该窗口与 `accounts.bill_day` 的对应关系需在生产数据上核对后才能作为归属依据。**
- **账务红线（本样本直接可见）**：描述里存在「自助还款」「网联自助转入」以及指向银行自身的负金额行，**负金额不等于退款**。导入前必须先按描述把行分类为消费 / 退款 / 还款或转入 / 费用利息，还款与转入**绝不写入 5010 支出科目**，也不作为负支出冲减统计；分类词表与归类结果属账务口径，需用户确认后冻结。
