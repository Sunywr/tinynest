## P2 已实现（2026-11-25，提交 `50b6752`）

范围为「银行汇总落库 + 按账期只读比对」，不含明细匹配、占位与自动入账。

- 迁移 `012_card_statements.sql`（SQLite 与 MySQL 各一份，两方言现各 12 个文件）新增 `card_statements` 与 `card_statement_sources`。表名故意避开 V1 已退役的 `credit_statements` / `credit_statement_items`，让 `tinynest-admin` 清理清单继续表示 V1 语义。MySQL 版只用 `CREATE TABLE IF NOT EXISTS` 与内联索引、约束，结构上可重跑。
- 契约：`POST /api/v1/accounts/{id}/credit-statement-sync?provider={qq|163}&version={n}` 返回 `{since,created,linked,conflicts,needs_review,items[]}`；`GET /api/v1/credit-statements` 返回 `{items:[{id,account_id,account_name,period_start_on,period_end_on,due_on,currency,amount_due_minor,status,review_reason,source_count,ledger_charge_minor,difference_minor}]}`，按期末、卡名、id 排序。路由预算由 70 提高到 72，实测 `Register wired 72 routes`。
- 幂等：账单唯一键 `household_id + account_id + period_end_on`；来源唯一键 `household_id + digest`，`digest` 为服务商、用户、IMAP UID、账户、期末、到期日、卡尾号、金额与币种的 SHA-256。同邮件重放不新增账单，同账期新邮件只增加来源。
- 与草案的偏离：来源键未使用 `UIDVALIDITY`。现行 IMAP 只读打开不解析 `EXAMINE` 响应，取该值需要改动协议层；改用内容摘要承担重放识别，UID 仅作为摘要输入保留。
- 只存「完整识别」的汇总（账期、非负人民币应还、无待核对标记）。金额冲突保留首次记录的银行金额，只补 `review_reason`；未识别邮件只计数，不落库。审计仅在有新账单或冲突时写一条 `sync_card_statement`。
- 账本比对：`period_start_on` 由卡片 `statement_day` 推导为上一账期期末的次日；未配置账单日时 `period_start_on`、`ledger_charge_minor`、`difference_minor` 一律为 `NULL`。`ledger_charge_minor` 在 SQL 层按家庭与账户码聚合同周期已入账消费（贷记卡科目取贷−借），与现行还款计划口径一致。
- 账务不变量：该路径不写 `transactions`、`journal_entries`、`journal_lines`，也不改账户余额；用例断言同步前后 `GET /accounts?include=credit_debt` 的 `total_debt_minor` 不变。
- 权限与隔离：写操作需成员以上与 CSRF，只读角色 403；未绑定或他卡 404；跨家庭账单与来源查询无结果，跨家庭来源行被 `(household_id, statement_id)` 复合外键拒绝。
- 并发：邮箱读取后与写入事务内各重验一次配置版本与绑定。停用或换码与拉取并发时返回 409 且零落库；`TestStatementSyncRechecksMailboxBeforeWrite` 在移除该重验后会退化为 200 并写入账单，已实测确认该用例对守卫敏感。

## 清理工具的账单表外键阻塞（2026-11-25 新发现）

`internal/dbadmin/tables.go` 的清理清单与 11 张身份白名单都没有迁移 005/009–012 新增的表，`Snapshot.Unclassified` 因此在空 V2 库上就报出 9 张表：`card_statements`、`card_statement_sources`、`statement_mailbox_configs`、`statement_mailbox_card_links`、`credit_statement_mailboxes`、`credit_statement_bindings`、`investment_accounts`、`investment_holdings`、`schema_meta`。

不只是报告噪音：`card_statements.account_id` 与 `statement_mailbox_card_links.account_id`（以及 010 的 `credit_statement_bindings.account_id`）都外键引用 `accounts(id)` 且无 `ON DELETE CASCADE`，而 `Purge` 只删 `DeleteOrder()` 里的表，所以一旦库里存在账单或绑定，`DELETE FROM accounts` 就会被拒。已补两条红测试记录触发条件，尚未修复，`go test ./internal/dbadmin` 当前不通过：

- `internal/dbadmin/purge_statement_tables_test.go:TestPurgeClearsCardStatementTables` → `dbadmin: delete from accounts: constraint failed: FOREIGN KEY constraint failed (787)`，`committed=false`，整笔事务回滚，身份与账本行未受损。
- 同一场景在 MySQL 8.4.7 上直接复现：`ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (...card_statements_ibfk_2...)`，回滚后 `accounts`/`card_statements` 仍各 1 行。
- `TestV2SchemaHasNoUnclassifiedTables` → 列出上述 9 张表。
- 影响面：生产 `tinynest_v2` 现有 2 条 `statement_mailbox_configs` 与 7 条 `statement_mailbox_card_links`，因此[生产清理手册](v2-prod-purge-runbook.md)在当前数据下必然失败，不能按手册直接执行。`investment_*` 只引用 `households`/`investment_accounts`，不阻塞删除，但会在清理后静默保留数据，使「业务表全空」的断言不成立。
- 待用户决定的口径（见「下一个可执行项」第 3 条）：哪些表按业务数据清理、哪些按身份/配置保留、`schema_meta` 是否像 `sqlite_sequence` 一样列为已知元数据。保留与清空都改变 `AGENTS.md` 写死的「11 张身份表白名单」和「45 张清理表」，不属于可自行决定的范围。

### HTTP 与权限

沿用 `/api/v1` 及现行错误结构。邮箱配置、测试及信用卡绑定已实现，拉取与对账端点为设计提案。

| 方法与资源 | 行为与权限 |
| --- | --- |
| `GET/PUT/DELETE /credit-statement-mailbox` | 读取、配置或换码、停用当前用户在当前家庭的邮箱。保存和停用需写权限与 CSRF。读取返回 `provider`、`enabled`、`masked_email?`、`version` 和 `key_ready`。保存提交 `email`、`auth_code`、`version`，连接验证成功才写库。停用提交 `version`，清除邮箱与授权码，并保留递增版本。过期版本返回 409 |
| `POST /credit-statement-mailbox/test` | 需要具有写权限的家庭会话和 CSRF。即时测试提交 `email` 和 `auth_code`，已保存测试只提交 `version`。成功返回 `{status:"connected"}`，操作限于 IMAP 登录和只读打开收件箱 |
| `GET /credit-statement-mailbox/cards` | 列出同家庭的启用信用卡，以及当前用户已绑定的停用信用卡。只返回账户信息与绑定状态 |

| `POST /accounts/{id}/credit-statement-preview?provider={provider}&version={version}` | 只允许当前配置拥有者从已绑定且启用的浦发或中信卡手动预览，需 CSRF。搜索近 30 天，限 8 封邮件和单封 512 KiB，读取后重新核对版本及绑定。仅返回识别出的日期、应还整数分及待核对原因 |

| `PATCH /credit-statements/{id}/reminder` | 未实现，仍为设计提案。有写权限的家庭成员关闭或恢复补录提醒，账单继续可补录 |

数据库查询按家庭限定账单、明细、绑定和账号。跨家庭 ID 返回 404，只读角色无写权限。邮箱网络连接使用预设服务商与证书校验。只有配置拥有者能测试、拉取或管理其邮箱，家庭管理员查看账单时也只获得账单业务字段。

邮箱授权码使用现有服务端邮件密钥进行 AES-GCM 加密，绑定到用途、家庭、用户、邮箱地址及配置版本。保存与停用同审计记录提交，审计记录只保存动作和配置归属。连接失败保留原配置。保存前复核账号权限与版本，已停用的配置无法再使用保存的授权码发起连接测试。

同地址换码保留绑定。停用邮箱或保存不同邮箱地址会清除旧绑定。绑定事务重新检查用户角色、邮箱版本和信用卡状态，绑定及审计同一事务提交。按现有家庭信用卡写权限授权，绑定只保存邮箱配置和账户的关联。银行邮件与卡片的匹配规则等待样本。

邮箱配置、测试及绑定接口接受 `provider=qq` 或 `provider=163`，省略时沿用 QQ。163 使用 IMAP TLS，认证后发送客户端 ID，再只读打开收件箱。两家邮箱的换码、停用和版本分别生效。[网易邮箱授权码帮助](https://help.mail.126.com/faqDetail.do?code=d7a5dc8471cd0c0e8b4b8f4f8e49998b374173cfe9171305fa1ce630d7f67ac286624f309a1a7089)

### 邮件预览验证

- 预览按绑定账户名称识别浦发、中信及括号中的卡号后四位。用收件箱的 IMAP 只读访问查找候选，按发件地址和账单主题筛选，对照卡号和人民币金额字段解析。预览只作核对，邮件发件地址匹配不代表真实性认证。
- 生产只读联调使用指定用户已经绑定的两张卡。两家邮箱均完成真实认证及只读读取。中信识别 1 封匹配邮件的应还金额。浦发查询成功，近 30 天无符合筛选条件的邮件。只记录数量，未导出邮件内容或授权码，未写入生产账本。
- 表单等宽对齐，绑卡页面将已绑定项置于未绑定项之前，并区分绑定和解绑按钮。Go 全量、vet、tidy、构建及 Playwright 93/93 通过。浏览器测试覆盖输入框对齐、分区、按钮样式和预览，使用模拟预览响应。账单明细解析、对账和 XLS 导入待实现。

### 待还与账务

- 首版提案将银行报告总应还及其账期显示在对应信用卡下，银行金额标注来源。账本净资产、总债务及发薪日前准备金额仍按原规则聚合，同一账期的银行报告不再加到现有汇总。银行到期日或金额与账本推导有差异时显示待对账。
- 仅总应还时保持待对账。比如银行报告应还 ¥1,200，账本中找到当期消费 ¥600，单凭两者不能把 ¥600 差额认作消费。待样本明确结转、费用、退款和还款后，再确定本期净消费。若之后另行引入占位，仍需确认占位金额、业务日期、支出分类及报表影响。
- 退款与还款必须分别识别。现行还款使用转账，退款没有可用的 V2 公共入账接口。未获得可验证规则的负项进入待核对。
