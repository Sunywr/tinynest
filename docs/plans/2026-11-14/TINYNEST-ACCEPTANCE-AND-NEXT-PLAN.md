# TinyNest 2026-11-14 最新代码验收与下一阶段实施计划

> 版本定位：**先确定真实交付基线，再择优继续 V0.1.1 收尾或进入 V0.1.2**。
> 审查来源：https://github.com/Sunywr/tinynest.git
> 重要限制：本计划编写时，外部环境无法读取 GitHub 仓库、Raw/API 或 git remote，因此**不代表对 2026-11-14 最新代码已作验收**。必须由 WorkBuddy 在具备仓库访问权限的工作区执行以下核验并填入真实证据。
> 旧基线：2026-11-13 用户提供的 V0.1 PR 修复报告中，复式记账、构建、迁移和隔离备份演练通过；当时 S3～S7 存在未实现项，CI/前端 E2E/PWA/双服务器仍待实测。本轮不可把旧结果当成最新状态。

## 1. 两个明确目标

1. **验收门禁 A：V0.1.1 开发基线是否真正完成**。用最新 Git SHA、源码、SQLite 迁移、Go/Vue 测试、浏览器操作及 CI 状态，判断信用账单、分期、固定负债、调度与首页统计的闭环。
2. **建设目标 B：V0.1.2 投资管理与家庭报表**。只有验收门禁 A 的关键账务路径达标，才增量补齐交易费率、持仓计算、分红和投资统计；已具备的功能只验证、不重写。若门禁 A 失败，先修 V0.1.1 阻断，再复核，不冒险推进与其耦合的新功能。

**本轮不以实现代码行数作为完成指标。** 合法的完成路径可以是“最新代码已经满足大部分要求 → 只补测试/修复/文档”。

## 2. 必须先做的现场审查

### 2.1 Git 基线

- 从当前工作区核实远程 URL、`main` / `feature/**` 最新 SHA、默认分支、待合并 PR、最近 20 个提交、工作树是否干净。
- 先执行 `git status --porcelain=v1`、`git branch -avv`、`git remote -v`、`git fetch origin --prune`、`git log --all --graph --decorate --oneline -25`。防止碰到未提交修改。
- 检查最新 `main` 是否已经包含 V0.1.1、PR 修复及 GitHub Actions；不能凭分支名断言。
- 只在可保护现有改动的前提下创建工作分支 `feature/tinynest-v0.1.2-investment-reports` 或使用独立 Worktree；如需要先修 V0.1.1，则分支名用 `fix/tinynest-v0.1.1-closure`。
- 不执行 `reset --hard`、`clean -fd`、强制推送、重写历史。

### 2.2 事实证据矩阵

每个模块必须有一行：`功能要求 / Git SHA / 源码文件:行号 / API 路由 / 数据库表或迁移 / Web 页面入口 / 运行测试用例 / 实际结果 / 缺口 / 等级`。

## 3. 第一验收门禁：V0.1.1

### 3.1 关键业务必须按实际数据库验证

1. **信用账单**：额度 20,000 元，信用消费 1,000 → 未还 1,000、可用 19,000；现金偿还 600 → 未还 400、可用 19,600；退款 300 退回信用工具 → 未还 100、可用 19,900；再还 100 → 未还 0。手续费和跨账单退款须独立处理。
2. **贷款信用支付**：本期房贷 2,000 元（本金 1,500 + 利息 500），使用信用卡支付 → 房贷本金 -1,500、利息支出 +500、信用卡负债 +2,000、现金不变；后续现金还信用卡 2,000，不能再次计支出或再次减少房贷本金。
3. **分期**：本金 3,000、费用 90、3 期，每期计划合计守恒。部分付款要明确本金与费用分配，**未确认时不能自行采取先本金/先手续费策略**。已付期次不被退款、提前结清流程静默删除。
4. **自动调度**：同一到期事项连续触发 20 次、服务重启补扫，最终只生成一个待处理业务键，且永远不自动认定已经付款。
5. **时间与隔离**：Asia/Shanghai 跨年、闰年二月和 28～31 日；同库两个 household，任一统计、详情、写入和定时投影不能串家。
6. **真实界面**：不是只打 API，需完整操作前端并截取无敏感数据的测试证据。

### 3.2 通过/失败规则

- 任一已确认财务事实生成不平衡分录、错误余额、跨家庭访问或重复付款 → `BLOCKED`，先修。
- 已实现但缺少可运行测试 → `UNVERIFIED`，不能算 PASS。
- 部分非核心页面/UI 仍未完成可列 P2，但不得冒充 V0.1.1 完整交付。
- 10 项业务口径（`docs/reviews/v0.1-accounting-decisions.md`）必须逐条核对。只有用户明确确认的，才可以标 `CONFIRMED_BY_USER`；仅在代码中实现不能视为确认。

## 4. 通过门禁 A 后进入 V0.1.2：投资与财务报表

### M1 — 投资产品及交易费率设置

- 账户与证券/理财产品关系可追溯，区分股票、ETF、其他理财。
- 佣金比例、最低佣金、交易印花税/其他税费、过户费及平台费均为**可配置规则**。不同市场和交易方向须有可选规则；不得把某个历史示例费率硬编码为真实最新费率。
- 账户可保存费率模板，单笔成交允许人工修正最终费用；交易保留 `fee_rule_snapshot`、自动计算与手工覆盖结果、修改原因。
- 历史成交不因为费率规则更新而重算，金额使用整数分/定点数，校验小额最低费用、零费率和精度。

### M2 — 成本、减仓、清仓与分红收益闭环

- 在既有移动加权平均成本实现上补齐 API / 页面 / 测试，不能重复写一套收益算法。
- 买入费用计入成本；卖出费用减少卖出净收入；部分卖出按卖出前单位成本结转；清仓成本归零、历史已实现收益保留；再次建仓不污染上个持仓周期。
- 分红记录税前、实缴红利税（可空）、税后到账、到账账户、到账日期；“未知税额”不得等同于 0。必要时区分 **已知净分红** 与 **待核验税额**，不擅自计算不确定的净收益。
- 手动更新价格/净值并显示来源与估值日期；过期估值标注“估值待更新”，不能宣称实时收益。
- 证券账户充值/提现是账户间转账，不计投资收益；投资买卖本金不能进入普通收支。
- 若已有相关功能，优先针对边界进行专项回归。

**确定性样例（单位人民币）**：

| 交易 | 结果 |
|---|---|
| 买入 100 股 × 10，手续费 5 | 成本 1005 |
| 再买 100 股 × 12，手续费 5 | 200 股，总成本 2210，单位成本 11.05 |
| 卖出 50 股 × 13，卖出费 5 | 净回款 645，结转成本 552.50，已实现收益 92.50 |
| 剩余 150 股，价格手填 14 | 剩余成本 1657.50，估值 2100，未实现收益 442.50 |
| 税前分红 100，已知税 10 | 净分红 90 |
| 合计 | 投资总收益 625.00；若采用累计含费买入成本 2210 为分母，则简单参考收益率 28.28%，不得称年化收益率 |

要单独检验佣金最低费用、整数分舍入、卖出超过持仓、红利税空值、估值缺失、同日先卖后买，以及连续减仓至清仓的残余成本。

### M3 — 投资收益、分红与家庭资产视图

- 账户视图：可用现金、持仓成本、手动估值、已实现/未实现/分红收益、最近估值日期。
- 资产汇总：家庭现金、证券账户现金、持仓估值、理财估值、信用/贷款本金负债、净资产。**禁止证券现金及投资账户转账重复归集。**
- 历史总收益：按明确公式显示收益金额与收益率分母；区分期间损益、历史累计投入、当前持仓收益，避免用同一个数字冒充不同财务口径。
- 项目/分类/成员/账户收支统计按日期和明细下钻，退款按净支出口径，转账和投资本金不混入消费。
- 日历范围支持自然月、自定义日到次月日、年初至今。统计值可通过 SQL 和业务分录重建。
- 如果用户尚未确定投资收益率口径，输出推荐方案和对照结果，保持 `PENDING_USER_CONFIRMATION`，不标为已批准规则。

### M4 — 可靠性、测试与可演示性

- 自动化：Go 单元+集成、Vue typecheck/build、浏览器 Playwright E2E、CI 真正运行；要有 12 条以上覆盖核心业务的端到端流程，相关新增业务必须有正/反例。
- 新增账务操作必须在同一 SQLite 事务写业务记录和分录；同一请求键并发 20 次只记一次；已入账只能冲正，不能物理删除。
- 无安全回退：setup token、Secure Cookie、可信代理、household 隔离、CSRF、限流必须继续通过。
- 从空库迁移与已有库升级都必须通过；隔离库备份、恢复并比较业务汇总，`quick_check=ok`、`foreign_key_check` 无错误。
- 若设备不可用，真实 iPhone PWA 和 A/B 双服务器 TLS 标记 `UNVERIFIED` 并进入独立生产门禁；不得写作已验收。
