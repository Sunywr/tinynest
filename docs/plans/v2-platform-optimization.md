## 2. 前端优化

| 优化项 | 为什么 | 如何验证 |
| --- | --- | --- |
| `App.vue` 拆分 | 单文件 3,041 行把路由、状态、视图与样式混在一起，无法按界面独立迁移、测试与并行开发 | 拆分后 `App.vue` ≈200 行；单文件 ≤300 行由脚本检查；E2E 覆盖五个界面 |
| 引入 `vue-router` 4（唯一新增依赖） | 需要 iOS 返回手势与深链；自研路由无法可靠处理浏览器历史与手势返回，也容易和弹层状态冲突 | `package.json` 依赖清单评审；iOS 返回手势 E2E；深链接刷新后落到正确界面；依赖审计确认无其他新增运行时依赖 |
| 设计 token 化 | 颜色、圆角、间距散落在组件里，无法保证唯一主题与后续一致性 | 扫描组件中硬编码颜色值（白名单排除 token 定义）；设计规范对照检查 |
| 移动安全区与 44px 触控 | 底部面板与导航在 iOS 手势区容易被遮挡；小热区在手机上误触 | 390×844 E2E 截图与元素边界断言；自动化检查可点击元素热区 ≥44×44 |
| 长列表 `content-visibility` | 按天分组的流水可能很长，首屏渲染成本高；浏览器可跳过屏外内容布局 | 长列表渲染耗时与滚动帧率对比；不支持该属性的浏览器回退为普通渲染且不报错 |
| 错误边界与离线提示 | 单个视图异常不应整页白屏；网络失败必须明确提示，不能伪造成功 | 注入视图异常验证错误边界；断网 E2E 校验「网络不可用，未保存」文案与禁用态 |
| LCP / CLS 预算 | 移动端首屏与布局稳定性直接影响记账体验 | Lighthouse / PerformanceObserver 在 390×844 与 1440×900 下测量；预算数值 P3 冻结（候选 LCP ≤2.5 s、CLS ≤0.1，UNVERIFIED） |
| 单主题不新增风格 | 设计规范只允许 A · 奶油团子；多风格会让 token、组件与验收矩阵翻倍 | 主题 token 扫描；设计评审确认无第二主题、无风格切换入口 |
| `api.ts` 收敛为薄客户端 | 当前请求封装混杂业务逻辑；统一薄客户端后错误、CSRF、幂等与离线状态只有一处实现 | 代码评审：`api.ts` 只负责请求构造、鉴权头、错误映射与类型；业务聚合逻辑在 `services/`；E2E 覆盖错误分支 |

落地要点：

- 目标结构：`App.vue` ≈200 行 + `router/index.ts` + `views/`（账单、记账面板、图表、资产、我的）+ `components/`（日组头、流水行、分类网格、数字键盘、环形图等）+ `composables/`（记账草稿、离线状态等）+ `services/`（接口聚合）。
- 路由唯一新增依赖为 `vue-router` 4；不得引入 UI 组件库、状态管理库或图表库替代现有实现。
- 离线提示只做状态与错误展示，V1 不做离线补记账队列。
- 性能预算的具体数值在 P3 标定并写入 CI 报告；未标定前不得宣称达标。

## 3. 后端优化

| 优化项 | 为什么 | 如何验证 |
| --- | --- | --- |
| 路由表集中声明并可断言路由数 | 140 条路由分散注册，无法一眼看清总量与边界，删除退役模块时容易漏网 | 路由集中注册；测试断言路由数 ≤55，并与契约文档逐条比对 |
| 中间件链固定顺序 | 顺序错误会导致未登录请求被限流、只读角色绕过写保护等安全缺陷 | 顺序固定为 `session → CSRF → viewer 只读 → 限流 → request-id`；顺序被改动的测试立即失败 |
| 统一错误码与中文文案 | 前端无法可靠区分错误类型；文案散落导致体验不一致 | 错误码表评审；契约测试逐项校验错误码与中文文案；前端错误分支 E2E |
| 分页统一 cursor | 偏移分页在并发写入下会重复或漏数据 | 契约测试：非法 cursor、超限 `limit`、边界页行为一致 |
| 幂等键统一中间件 | 记账写操作重复提交会产生重复分录，破坏账务 | 相同幂等键重复 POST 返回同一结果；测试覆盖超时重试场景 |
| 删除死代码 | 无调用点的规则（如 `OpeningLiability`、`InsurancePayment`）增加阅读成本并误导后续开发 | 引用检索 + deadcode 检查；删除后 `go test ./...` 全绿；删除清单写入评审记录 |
| 结构化日志与慢查询阈值 | 生产排障需要可检索字段；慢查询是统计性能问题的第一信号 | 日志字段 schema 评审；慢查询阈值可配置，默认值 P2 冻结（UNVERIFIED）；测试断言日志字段齐全 |
| `go mod tidy -diff` 保持 | 依赖漂移会引入未评审的模块与供应链风险 | CI 执行 `go mod tidy -diff`，必须无输出 |
| 后端非测试代码 ≤7,000 行 | 与路由收敛同步控制复杂度 | 行数统计脚本排除 `_test.go`；在 P2 门禁中执行 |
| 复式内核保留、对外简化为「流水」 | 账务正确性依赖分录；对外暴露 `journal_*` 会让界面与账务耦合 | 代码评审确认 API 只暴露 `transactions` / `accounts` / `stats`；分录表不出现在 API 契约中 |

落地要点：

- 中间件顺序是安全约束：`session` 之后才能识别用户，`CSRF` 之后才能接受写请求，`viewer` 只读必须在业务处理器之前拦截写操作，`限流` 在身份识别之后按用户维度生效，`request-id` 最后注入以覆盖全链路日志。
- `GET /accounts/{id}/journal` 只读暴露账户分录，用于账户明细；其余分录结构不对外。
- 慢查询阈值与结构化日志字段在 P2 冻结并写入配置；生产观测结果 UNVERIFIED。

## 4. 数据端优化

| 优化项 | 为什么 | 如何验证 |
| --- | --- | --- |
| 单一迁移器 + checksum + baseline 守卫 | 现状 SQLite 21 个版本、MySQL 14 个版本双轨且版本号不齐，迁移状态不可信；启动期还有 `UPDATE categories SET parent_id=NULL` 的破坏性副作用 | 迁移测试：from-zero 建库、checksum 篡改拒绝、版本断档拒绝、baseline 不符拒绝启动；迁移清单与二进制版本一致 |
| 统计一律由分录派生 | 流水金额累加会产生账实不符；分录是唯一账务事实来源 | 统计测试用 `journal_lines` 构造数据；统计结果与分录合计对账；代码评审确认无流水金额累加路径 |
| `household_id` 作用域静态检查 | 先全库聚合再过滤会泄露跨家庭数据，这是历史审查中的高危问题 | 静态检查规则（SQL 查询必须带 `household_id` 条件）；跨家庭数据泄露测试；代码评审 |
| 索引评审 | 记账列表与统计查询缺少针对性索引会造成慢查询 | 候选索引 `transactions(household_id, occurred_on, type)`、`journal_lines(account_code, entry_id)`；`EXPLAIN` 计划评审；慢查询日志复核 |
| 备份恢复自动化 + 保留策略 | G5 要求每阶段有可回滚备份，手工备份不可靠 | 定时备份任务 + 校验（SHA-256）；恢复演练到隔离实例；旧库与备份保留 ≥30 天 |
| CI 每次跑迁移与回滚演练 | 迁移只在生产首次执行才会暴露问题 | CI 在 SQLite 与 MySQL 上执行 from-zero 迁移与回滚 / 重建演练；失败即红 |
| 表 55 → 27 收敛 | 退役模块留下大量空表与孤儿数据，增加清理与误操作风险 | DDL 清单评审；新库基线建表数断言；v1 库数据清理由清理工具承担（只删数据） |

落地要点：

- 清理工具只做数据删除（DML），保证单事务可回滚；表结构收敛由 V2 新库基线承担，两者不能混为一个步骤。
- 无 `ON DELETE` 级联是现状约束：删除与清理必须显式按依赖顺序处理，禁止依赖数据库隐式级联。
- 索引变更必须与新表 DDL 一起进入迁移评审，不接受上线后临时加索引。
- 备份与恢复的保留策略：旧库与备份 ≥30 天；恢复演练结论写入评审记录，未演练前相关门禁 UNVERIFIED。

## 5. V2.1 可选：`internal/api` 分包重构

V2.1 可选分包：把 `internal/api`（95 文件、21,503 行）按职责拆为 `platform` / `store` / `bookkeeping` / `identity` / `httpapi`。该重构**不在 V2 范围**，需要独立评审窗口。

| 目标包 | 职责（建议边界，评审冻结） | 为什么 | 如何验证 |
| --- | --- | --- | --- |
| `platform` | 配置、日志、时钟、数据库连接、迁移器 | 基础设施被各业务包复用，避免循环依赖 | 包依赖图无环；仅移动与重命名 |
| `store` | 持久化与 SQL 访问 | SQL 与业务规则分离，便于 `household_id` 静态检查 | 每个 SQL 调用点仍显式限定家庭作用域 |
| `bookkeeping` | 流水、账户、预算、统计领域逻辑 | 记账是 V2 核心，独立后可单独测试 | 领域测试全绿；API 行为不变 |
| `identity` | 用户、会话、权限、邀请、邮件 | 身份与记账解耦，安全边界清晰 | 权限测试与邮件测试全绿 |
| `httpapi` | 路由声明、中间件、请求响应、错误码 | 路由集中后可断言路由数 | 路由断言测试通过；中间件顺序测试通过 |

约束与验证：

- 仅机械改动：包边界、导出符号与依赖方向；不夹带行为变更、不顺手改逻辑。
- 每一步单独 PR，diff 中只有移动与重命名；`go build ./...` 与全量测试必须全绿。
- 包边界、依赖方向与顺序在独立评审窗口冻结；评审记录与回滚点齐备后才允许合入。
- 未执行前，本节的收益与风险均为 UNVERIFIED；不得以「更清晰」为由跳过评审。
