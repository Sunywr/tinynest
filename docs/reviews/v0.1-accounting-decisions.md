## 1. 单家庭单管理员登录，其余成员仅为交易归属档案

- **status**: `PENDING_USER_CONFIRMATION`
- **当前代码行为**：`POST /api/v1/setup` 在空库时创建**唯一一个** `households` 行和**唯一一个** `role='admin'` 的 `users` 行；初始化后该端点恒定返回 `409 conflict`，无注册第二个登录账号的 HTTP 路径。`household_members` 表存在，`accounts.owner_member_id` 可指向成员档案，但没有成员 CRUD / 登录 / 权限 API。会话与 CSRF 全部绑定单个 admin。
- **代码位置**：`apps/api/internal/api/setup.go:95-125`（条件 INSERT + 唯一 admin）、`apps/api/internal/api/setup.go:135+`（会话）、`apps/api/internal/db/migrations/001_base.sql`（`users`、`household_members`）、`apps/api/internal/db/migrations/003_transactions.sql:8`（`owner_member_id`）。
- **推荐值**：V0.1 维持单管理员；成员只作归属标签，不引入多用户权限。
- **影响的统计/迁移/测试**：若改为多成员可登录，需新增 `users` 多行、角色与权限列、会话主体切换，并对**所有** `household_id` 隔离 SQL 增加成员级过滤；`TestHouseholdIsolation`、`TestSessionCookie*`、CSRF 与审计测试全部要重做。迁移需追加新版本，不得改写 001。
- **待确认点**：是否允许配偶/子女独立登录；若允许，数据可见范围如何划分。

## 2. 银行卡/微信/支付宝余额统一归入现金类账户

- **status**: `PENDING_USER_CONFIRMATION`
- **当前代码行为**：`accounts.kind` 只有 `('cash','securities','wealth')` 三类，差异靠自由文本 `subtype` 表达；现金类统一挂 `ledger_code = '1010:<account id>'` 科目。银行卡、微信、支付宝都只能建成三个 `kind='cash'` 的独立账户，没有独立科目或独立余额口径。
- **代码位置**：`apps/api/internal/db/migrations/003_transactions.sql:3-14`、`apps/api/internal/ledger/subjects.go:6`（`SubjCash = "1010"`）、`apps/api/internal/api/dashboard.go:120`（现金流口径注释）。
- **推荐值**：保持三类 + `subtype` 标签，不为第三方钱包单设科目。
- **影响的统计/迁移/测试**：若拆分科目，净资产、现金流、账户余额三套聚合 SQL 的 `ledger_code` 前缀匹配都要改；`TestHouseholdIsolation` 的 `1010:` 造数、`db.Balance` 的科目参数需同步调整。迁移需追加字典/科目版本，历史分录须保留原科目以保证可重建。
- **待确认点**：微信/支付宝的「零钱 + 理财」混合余额是否需要拆账户；`subtype` 是否需要受控枚举。

## 3. 账单周期按用户录入起止日/还款日，允许单期人工修正

- **当前代码行为**：创建信用工具时录入 `cycle_start_day`、`cycle_end_day`、`due_day`、`due_month_offset`；每笔信用消费按发生日 `occurred_on` 经 `credit.CycleFor` **自动**归入账单周期，生成 `credit_statements`（`unbilled`）。**没有单期人工修正起止日/还款日的 HTTP API**；账单 `status` 也只在还款时变为 `partial/paid`，不随日期自动判定逾期（见 `IMPLEMENTATION_REPORT.md` 第 9 节已知问题 4，S3 未完成）。
- **代码位置**：`apps/api/internal/api/credit.go:29-60`（`assignStatement`）、`apps/api/internal/api/credit.go:75-120`（创建信用工具）、`apps/api/internal/credit/cycle.go:51`（`CycleFor`）、`apps/api/internal/api/credit.go:182-205`（账单列表）。
- **推荐值**：V0.1 保留自动归属，允许对单期账单做人工覆盖（需记录修正原因与审计）。
- **影响的统计/迁移/测试**：需新增「人工周期覆盖」字段与写接口（追加迁移版本），并保证 `assignStatement` 的 `(statement, source_type, source_id)` 幂等键不被覆盖破坏；月度支出、负债到期、现金流三套统计都要改用修正后的 `due_on`。测试需补跨月/跨年、重复修正、修正后还款。

## 4. 分期创建时一次性确认完整消费，后续按期结清负债

- **status**: `PENDING_USER_CONFIRMATION`
- **当前代码行为**：`handleCreateInstallment` 在创建合同时按 `principal_minor + total_fee_minor` 一次性生成完整消费分录并写入 `installment_schedule_items` 逐期计划；后续 `handleInstallmentPayment` 只做「现金 → 负债」的清偿分录，不再重复确认消费。
- **代码位置**：`apps/api/internal/api/credit.go:309-395`（创建合同 + 逐期计划）、`apps/api/internal/api/credit.go:427+`（分期付款）、`apps/api/internal/db/migrations/004_credit.sql`（`installment_contracts` / `installment_schedule_items`）、`apps/api/internal/ledger/rules.go`（对应分录规则）。
- **推荐值**：维持「创建时一次性确认」，按期结清负债。
- **影响的统计/迁移/测试**：若改为按期确认消费，月度支出统计口径、合同创建时的借方科目、退款/提前结清的冲正路径都会改变；需要重写 `ledger` 分录规则与 `api_test.go` 的 S3 用例，并新增历史数据补录迁移（风险高）。
- **待确认点**：大额分期是否要求按期确认；提前结清时未确认部分如何处理。

## 6. 投资成本用移动加权平均法（非 FIFO）

- **status**: `PENDING_USER_CONFIRMATION`
- **当前代码行为**：`invest.Position` 用移动加权平均维护 `TotalCostMinor`，买入重算均价、卖出按均价结转已实现盈亏；**没有 FIFO / 批次表**。`quantity_scaled` 为整数缩放数量，金额一律整数分。
- **代码位置**：`apps/api/internal/invest/cost.go:29`（`NewPosition`）、`:57`（`Buy`）、`:82`（`AvgCostMinorPerUnit`）、`:95`（`Sell`）、`apps/api/internal/db/migrations/006_invest.sql`（`investment_positions` 无批次列）。

- **影响的统计/迁移/测试**：若改 FIFO，需要新增买入批次表与消耗顺序（追加迁移版本），`Sell`、`RealizedPnLMinor`、持仓成本、收益率全部重算，历史已实现盈亏需按新法重述（破坏性高）。测试需补多次买入后部分卖出、零成本边界、缩放取整。
- **待确认点**：税务/券商口径是否要求 FIFO；卖出数量超过持仓时的处理。

## 8. 房贷/贷款每期本金利息由用户录入，不自动推算等额本息

- **status**: `PENDING_USER_CONFIRMATION`
- **当前代码行为**：数据表已预留 `debt_contracts`（`kind IN ('mortgage','loan','insurance','other')`、`remaining_principal_minor`）与 `debt_schedule_items`（`principal_minor` / `interest_minor` / `fee_minor` 分期拆分），`schedule/generate` 会读取 `debt_schedule_items` 生成待办。**但没有房贷/保险合同的 HTTP API（S4 未实现），也没有任何等额本息/等额本金推算代码**；当前只能由测试或脚本直接写表。也就是说「用户录入」这条路径在 V0.1 尚未真正可用。
- **代码位置**：`apps/api/internal/db/migrations/005_debt.sql:41-78`、`apps/api/internal/api/credit.go:520-560`（`handleGenerateDueItems` 读 debt 计划）、`IMPLEMENTATION_REPORT.md` 第 8 节 S4。
- **推荐值**：不自动推算，由用户逐期录入本金/利息；但**必须先补齐 S4 的 HTTP API**，否则该口径无法落地。
- **影响的统计/迁移/测试**：补齐 S4 才谈得上口径确认；若改为自动推算，需要利率、期数、还款方式字段（追加迁移版本）与摊销算法，负债余额、现金流预测、到期事项全部受影响。测试需补等额本息/等额本金、尾差、提前还款重算。
- **待确认点**：是否接受「V0.1 只能手工写表」这一现状；若不接受，S4 应列为合并前还是发布前必修。

## 9. 收益率 = 总收益 / 累计买入成本，不称年化

- **status**: `PENDING_USER_CONFIRMATION`
- **当前代码行为**：`TotalReturn = 已实现盈亏 + 未实现盈亏 + 净分红`；`ReferenceReturnBPS` 以 `cumulativeBuyCostMinor` 为分母返回基点，代码注释与首页 `investment_valuation_note` 均明确「不是年化收益率」。分母为 0 时返回 `ErrInvalidCost`。
- **代码位置**：`apps/api/internal/invest/cost.go:137-155`、`apps/api/internal/api/dashboard.go:130`、`apps/api/internal/api/investments.go:290-330`（累计买入成本汇总）。
- **推荐值**：V0.1 只用该参考收益率，不做年化、不做时间加权。
- **影响的统计/迁移/测试**：若引入年化/XIRR，需要每笔现金流日期与持仓市值时间序列，统计端点与前端展示都要改；需补「多次买卖 + 分红 + 跨年」边界测试。当前口径下也需补「累计买入成本为 0」「全部卖出后仍显示历史收益」测试。
- **待确认点**：分母用「累计买入成本」还是「平均占用资金」；全部清仓后是否继续展示。

## 10. 退款跨月：现金流按实际退款日，项目净支出按原交易减累计退款

- **status**: `PENDING_USER_CONFIRMATION`

- **代码位置**：`apps/api/internal/api/transactions.go:359-460`（退款创建）、`:460-480`（`net_expense_minor`）、`apps/api/internal/api/dashboard.go:110-135`（三套口径）、`apps/api/internal/db/migrations/003_transactions.sql`（`refunds` 表）、`apps/api/internal/api/api_test.go:234-245`（跨月净支出用例）。
- **推荐值**：维持「现金流按实际退款日、项目净支出按原交易减累计退款」的双口径分离，并在 UI 明示二者不可相加比较。
- **影响的统计/迁移/测试**：若改为「退款计入退款当月支出」，月度收入/支出、项目汇总、预算对比都会变；需补跨月、跨年、部分多次退款、退款超过原交易额的边界测试（当前仅有一条基础用例）。已入账分录不可改，只能追加冲正。
- **待确认点**：退款超过原交易额时是否报错；跨年退款是否影响上年报表重述。
