# 飞书邮件接入与上线说明

2026-11-18，已部署生产，发布目录标识 `mail-20261118-1640`（首次部署基线为 `397289c` 加邮件功能改动）。发件公共邮箱为 `admin@tinynest.cn`。

## 功能与权限

- 设置 → 邮箱与安全：验证绑定、更换邮箱、修改密码及公告订阅。
- 登录 → 忘记密码：通过已验证邮箱找回；修改成功撤销所有会话。
- 注册须验证邮箱，家庭邀请和审批仍然生效。旧账号的资料邮箱不自动获得验证状态，不影响登录和记账。
- 站点管理员额外看到“系统邮件”，可动态修改飞书凭据、测试并保存；家庭管理员没有此权限。配置测试失败保留旧版本，页面显示最近测试结果。
- 家庭管理员可向本家庭已验证、启用且订阅公告的账号发送纯文本公告，先预览人数再确认。发信前重新检查收件资格。
- 普通资料接口只接受原邮箱值，不能直接变更或清空地址。家庭管理员不能直接重置密码，应让成员自行找回；无法访问邮箱时使用受控恢复命令。

## 服务器准备（B 机）

先备份数据库并记录现有 API、Web 版本。构建 `go build -o tinynest-api ./cmd/server` 和 `go build -o tinynest-mail-admin ./cmd/mail-admin`。

生成一次邮件加密密钥，目录由 root 管理。以下路径是部署模板；不可覆盖已有密钥：

```sh
install -d -m 0700 /etc/tinynest/credentials
/opt/tinynest/api/tinynest-mail-admin -action generate-key -key-file /etc/tinynest/credentials/mail-key
chmod 0600 /etc/tinynest/credentials/mail-key
```

在 API 的 systemd 服务中添加：

```ini
LoadCredential=mail-key:/etc/tinynest/credentials/mail-key
```

也支持 `TINYNEST_MAIL_KEY_FILE` 指向服务可读的受保护文件。密钥必须恰好 32 个原始字节，不能使用十六进制文本。保留并单独加密备份密钥；数据库备份不包含解密能力。不要直接替换密钥，现有密文会无法读取。未配置密钥时继续支持登录与账务，邮件配置不可保存、验证码不可发送。

启动新版 API 自动应用 SQLite 013 或 MySQL 006 增量迁移。旧邮箱保留，验证身份表初始为空。授予权限必须提供核实后的用户 ID，命令使用与 API 相同的数据库配置和凭据读取环境：

```sh
/opt/tinynest/api/tinynest-mail-admin -action grant-site-admin -user-id '<核实后的用户ID>'
```

不能按登录名自动提权；无网页提权入口。撤销使用 `-action revoke-site-admin`。systemd 的 LoadCredential 只在服务进程内提供，运维命令需另行通过受保护文件配置 MySQL 密码读取路径，不把密码放进命令行。

## 页面配置与生产验收

1. 授权的站点管理员通过 HTTPS 登录，进入设置 → 系统邮件。
2. 保留 `smtp.feishu.cn`，选择 465 SSL/TLS（或 587 STARTTLS），填写公共邮箱账号和新的专用密码，填写指定测试收件地址及当前登录密码。
3. 勾选启用，测试并保存。测试计入额度；只有 SMTP 接受测试邮件后才切换配置。密码不再回显，留空保留当前密码，无需重启 API。
4. 飞书当前截图限额为每日 100 封，默认公告最多 20 封。计数按上海日期，重试和配置测试也保守计数；必须核对飞书实际额度及日界线后再调整。
5. 在外部测试邮箱确认实际收到邮件并检查 SPF、DKIM、DMARC 结果，验收注册及审批、邮箱变更、密码修改/找回和少量测试公告。SMTP 接受不等于最终送达。
6. 未配置服务前注册不能跳过邮箱验证；已有账号照常登录记账。上线后尽快配置，避免注册暂时不可用。

队列每两秒处理一封，安全验证优先。临时故障最多尝试四次，永久 SMTP 5xx 失败停止重试。进程重启后恢复超时发送任务，结果不明确时可能重复投递。完成、取消或过期后清空加密邮件正文。页面可刷新公告投递状态和全站额度。

受控恢复命令仅用于核实身份且无法使用邮箱的账号。新密码放在临时受保护文件中，执行后按运维策略清理；命令修改密码、撤销会话和挑战并写审计：

```sh
/opt/tinynest/api/tinynest-mail-admin -action recover-password -user-id '<核实后的用户ID>' -password-file /secure/replacement-password
```

## 回滚边界

回滚前暂停对外注册、邮箱变更和密码操作。恢复上一版 API/Web 会恢复旧版较弱的账号接口，不能把代码回滚当作安全降级的长期方案；保留新增表及邮件密钥。旧版 MySQL 迁移器拒绝高于 005 的版本：紧急回滚需先停新版服务，仅删除 006 的迁移登记行，保留新增表，再启动旧版。重新升级时 006 的 CREATE TABLE IF NOT EXISTS 可重跑并补回登记。此操作只能在确认回滚目标版本与迁移集合后执行。若需要恢复备份，必须恢复对应数据库和匹配密钥，并核对会话与验证身份。部署前后都验证 healthz、readyz、HTTPS、家庭权限和发信状态。

## 每个收件邮箱每日三封（2026-11-18）

注册：填写邮箱 → 发送六位验证码 → 在十分钟内提交验证码、登录名和密码 → 按原邀请码/审批流程加入家庭。
修改密码：已验证邮箱 → 当前密码 → 邮箱验证码 → 新密码与确认 → 撤销全部会话并发送安全通知。未验证的旧账号先完成邮箱绑定。

同一收件邮箱的注册、绑定、改密、找回、安全通知、公告、配置测试共用每天三次投递尝试额度。邮箱去除首尾空格并统一小写，按 Asia/Shanghai 零点重置；失败和不确定结果保守计数，重试也消耗次数，不保证最终送达。密码操作完成后的通知若超限会标记为 daily_limit，不回滚已经完成的密码修改。

SQLite 014 / MySQL 007 增加按日期和邮箱的计数表。原子条件更新保证不同 API 实例和并发请求不能超过三次；全站额度不足时同事务回滚邮箱预留。排队前同时检查已发送及有效待发送任务，投递前再次检查；过期和已被替代的验证码不消耗投递次数。额度耗尽返回 429 email_daily_limit，公告预览会检查全部收件地址。

每日额度从此版本启用后开始持久化计数，不把旧版缺少逐次投递日期的历史队列猜测为当日发送；已有全站计数继续保留。新增表保留；回滚到此前 MySQL 006 版本前需停服务并移除 007 迁移登记行，否则旧版版本检查会拒绝启动。回滚版本不具备三封限制，不作为长期运行方案。
